### A2. Create the read-only role

**CORRECTION — the draft's grants were on the wrong schema.** Every table lives in `logistics`
(`002_create_schema.sql:1`), not `public`. Granting only on `public` yields a role that can connect
and do nothing — every query fails with `permission denied for schema logistics`. Corrected:

```sql
CREATE ROLE claude_ro LOGIN PASSWORD 'REPLACE_WITH_STRONG_RANDOM';
GRANT CONNECT ON DATABASE postgres TO claude_ro;

-- the schema that actually holds the data
GRANT USAGE  ON SCHEMA logistics TO claude_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA logistics TO claude_ro;
ALTER DEFAULT PRIVILEGES IN SCHEMA logistics GRANT SELECT ON TABLES TO claude_ro;

-- public: PostGIS may be installed here, and it costs nothing to include
GRANT USAGE  ON SCHEMA public TO claude_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO claude_ro;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO claude_ro;

-- PostGIS functions live here on Supabase; needed for the S3 geometry queries
GRANT USAGE ON SCHEMA extensions TO claude_ro;

-- migration ledger, if the Supabase CLI ever wrote one (see A2 note below)
GRANT USAGE  ON SCHEMA supabase_migrations TO claude_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA supabase_migrations TO claude_ro;
```

If the last two lines error with `schema "supabase_migrations" does not exist`, that is expected —
`README.md:16` documents applying migrations **by hand** and there is no `supabase/config.toml`, so
the CLI ledger may never have existed. Skip them. S5.2 of the audit file detects applied migrations
by probing for the objects they create, independently of the ledger.

Verify the role cannot write. **CORRECTION — test against `logistics`, not `public`.** On PostgreSQL
15+ `public` no longer grants `CREATE` to `PUBLIC`, so a `CREATE TABLE` there fails for every role
regardless of these grants — it would pass while proving nothing about the grants just issued.

```sql
SET ROLE claude_ro;
CREATE TABLE logistics._should_fail (x int);   -- expect: permission denied for schema logistics
SELECT count(*) FROM logistics.buildings;      -- expect: a number, not an error
RESET ROLE;
```

Both must hold. Failure on the second means the grants did not take; success on the first means
stop — the role can write.

### Task 1 — the query files — DONE

Two files, all `SELECT`, both under the commit ceiling:

each commit under the ceiling; both motivations are real and recorded, not one dressed as the whole.

**CORRECTION — one requested query cannot be written as specified.** S3 asked for a distinct count
of medallion / licence / vendor identifiers. No such column exists: `stop_events` (`003:17-28`) is
`id, source_id, event_type, location, event_timestamp, dwell_seconds, passenger_count,
source_dataset, batch_id, created_at`, and `stops.py:88-93` persists only lat/lng, timestamp,
`passenger_count`, `'nyc_tlc'` and `batch_id` — TLC's vendor and licence fields are dropped at ingest
and are not recoverable. Flagged in place as `NOT RUNNABLE AS SPECIFIED`, with `source_dataset` /
`batch_id` / `source_id`-year as the nearest proxies.

Two further mismatches, handled in place rather than guessed at: `building_scores` timestamps are
`computed_at` not `created_at` (`003:66`); and `stop_events` has one `event_timestamp` discriminated
by `event_type` (`003:20-22`), so per-event min/max is a grouping.
