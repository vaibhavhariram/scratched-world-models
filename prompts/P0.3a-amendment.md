## 2. Ledger probe — APPLIED, and it now cannot raise

Ordering the ledger query last and commenting it out was a workaround, not a fix. Replaced.

`M4` is the presence check, returning a clean boolean rather than a regclass:

```sql
SELECT to_regclass('supabase_migrations.schema_migrations') IS NOT NULL AS ledger_present;
```

`M5` reads the contents without a direct relation reference. A plain `SELECT ... FROM
supabase_migrations.schema_migrations` raises at parse time, before any `WHERE` or `CASE` could gate
it — the planner resolves the relation regardless of runtime conditions. So the read is deferred
into `query_to_xml()`, whose argument is a string parsed only at execution, and gated by `CASE`,
which does not evaluate its `THEN` branch when the condition is false:

```sql
SELECT CASE WHEN to_regclass('supabase_migrations.schema_migrations') IS NOT NULL
            THEN query_to_xml('SELECT * FROM supabase_migrations.schema_migrations ORDER BY version',
                              false, true, '')
       END AS ledger_contents;
```

Returns NULL when the ledger is absent. `query_to_xml` needs a libxml-enabled build, standard on
Supabase; the fallback is noted in the file. `SELECT *` rather than a column list because the
ledger's columns vary by CLI version and naming `name` raises `42703` on older ones.

`p0_migration_state.sql` now has no statement that can raise on a missing relation, so the file is
safe in every run mode — psql, whole-file paste, section paste. Run mode is no longer a constraint
on its layout.

### Other probes depending on a relation of unknown existence — there are others

Asked for a list. In `p0_migration_state.sql`, none: M1 and M3 already use `to_regclass`, and M2
reads only catalogs.

In `p0_db_state.sql`, **every data query**. S1.2, S2.1–S2.5, S3.1–S3.4 and S4.1–S4.3 all reference
`logistics.<table>` directly and all raise `42P01` if migration 003 was never applied. Only S1.1,
S1.3 and S1.4 are catalog-only and safe.

Deferring twenty-odd statements through `query_to_xml` would make the file unreadable and unusable
as the audit artifact it exists to be — the XML wrapping would obscure exactly the numbers a reader
is there to check. Handled structurally instead: every table referenced in `p0_db_state.sql` comes
from migration 003 and nothing else, so one non-NULL M1 row certifies that all of them resolve. The
header now directs the operator to run `p0_migration_state.sql` first, and `run_db_audit.sh` runs
them in that order unconditionally.

## 3. psql invocation — CONFIRMED BROKEN, fixed

The diagnosis was correct and is reproducible:

```
FAKE_VAR="$(...)" sh -c 'echo $FAKE_VAR'   ->  child sees env FAKE_VAR=[hello]
FAKE_VAR="$(...)" /bin/echo "[$FAKE_VAR]"  ->  argv received: []
```

The assignment populates the child's environment, but argv is expanded by the parent shell in the
same phase, before that assignment is visible to it. `psql` would have received an empty connection
string, fallen back to local socket defaults, and failed with an error about a missing local role or
socket — pointing a debugging cycle at the wrong thing entirely.

Replaced by `scripts/run_db_audit.sh`. Nothing secret reaches argv; the URL is decomposed into
`PG*` variables and `psql` is invoked with no connection argument. `set +x` and `umask 077` are set,
and the only status line prints user, host, port and database — never the password.

**One deviation from the sketch, deliberate.** The sketch used `set -a; . workers/.env; set +a`.
That exports *every* key in the file, including `DATABASE_URL` — the write credential — into this
process and all its children, which contradicts the standing rule to never read any key but
`DATABASE_URL_RO`. The script extracts only the `DATABASE_URL_RO` line instead. Same structure, same
`PG*` outcome, without loading the drop-capable credential into memory.

Percent-encoded passwords are parsed with `urllib` rather than by splitting on `:` and `@`, which
would corrupt any password containing those characters. Verified against
`p%40ss%3Aw%2Frd` → `p@ss:w/rd`.
